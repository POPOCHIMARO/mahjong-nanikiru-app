- 依頼の理解：D.3.2で保留した候補別の厳密受け入れを、情報漏洩を防ぎながら実用時間で計算し、再学習できる設計を残す。
- 今回の完了条件：本書に計算定義、行動別の投影、キャッシュ契約、性能予算、再学習手順、D32A-01〜08の受入試験を記載し、JSON構文と参照先と開発計画の整合検査が通る。
- 今回の変更対象：本書、`d3-development-plan.json`、`calibration/README.md`。
- 今回の対象外：実行コード、テスト、学習済みモデル、生成データ、アプリ、原牌譜、将来評価予約台帳。
- 想定リスク：鳴き牌の二重計上、切った牌の残数への復帰、別視点の特徴の混用、特徴実装完了をモデル採用と取り違えること。

D.3.2aの実装完了は、厳密特徴の全件生成と検証、予算内の再学習、再読込評価一致までとする。
希少行動の未識別、応答率の較正不一致、他の未実装特徴は別のholdとして残す。
厳密受け入れを追加すれば相手モデル全体が採用可能になる、とは仮定しない。

## 3. 厳密受け入れの定義

受け入れは、次の一枚でシャンテンが下がる牌種と、その視点からまだ見えていない枚数とする。
実際の山の残数や和了確率を表すものではない。
役とフリテンを含む和了可否は既存の合法手生成が扱う。

```text
h[t]     = 投影後の自家の伏せ牌枚数（赤を通常五と合算した34種）
m        = 固定面子数（暗槓も1面子、加槓では増やさない）
v[t]     = 判断時点の公開済み牌枚数
v_a[t]   = 候補を投影した後の公開済み牌枚数
s        = shanten(h, m)
I(h,m)   = {t | h[t] < 4 かつ shanten(h + e_t, m) < s}
r_a[t]   = 4 - h[t] - v_a[t]
E        = {t in I(h,m) | r_a[t] > 0}
ukeireKinds = |E|
ukeireCount = sum(r_a[t] for t in E)
```

APIは長さ34、整数0〜4、固定面子数0〜4を検査する。
受け入れAPIに渡す伏せ牌の合計は`13 - 3*m`とし、加牌後は`14 - 3*m`になる。
`h[t] + v_a[t] > 4`、牌数不一致、存在しない牌の消費はエラーとして報告する。
負の残数を0に丸めて不正な入力を隠さない。
面子手以外の計算は`m == 0`の場合だけ有効にする。

形の計算結果はシャンテンと34bitの`improvingMask`で保持する。
公開残数が0になった牌をmaskから消して保存すると別の局面へ再利用できないため、残数の適用は後段で行う。
赤の有無、手出しとツモ切りで同じ牌姿になる場合はこの計算を共有するが、学習上の行動は統合しない。

## 4. 行動別の投影

候補評価は状態のコピー上で行い、元の手牌、公開列、河、ドラ表示を変更しない。
入力は行動する家の手牌、公開prefix、その時点の合法候補だけとする。

| 行動 | 受け入れを計算する状態 | 公開枚数への追加 |
|---|---|---|
| `discard`、`riichi_discard` | 指定牌を1枚除いた手牌。固定面子数は同じ | 捨てる牌1枚 |
| `pass` | 応答者の現在の手牌。応答対象の捨牌または加槓牌は既に公開済み | なし |
| `chi`、`pon` | `consumed`を除き固定面子を1増やす。合法な後続打牌ごとの手牌を評価し、下記の順で一つ選ぶ | `consumed`と後続打牌。鳴かれた牌は追加しない |
| `daiminkan` | `consumed`の3枚を除き固定面子を1増やした、嶺上前の手牌 | `consumed`の3枚だけ |
| `ankan` | 指定牌を4枚除き固定面子を1増やした、嶺上前の手牌 | 指定牌4枚 |
| `kakan` | 加える牌を1枚除いた、嶺上前の手牌。固定面子数は同じ | 加える牌1枚 |
| `ron`、`tsumo` | 終局行動としてシャンテンを-1、受け入れ枚数と種類数を0、適用フラグを0に固定 | 受け入れ計算をしない |

チーとポンの後続打牌は、残る牌から既存`kuikae_forbidden_tile34`の禁止牌を除いて列挙する。
応答対象牌は公開prefixの該当捨牌から取り、後続の実打牌や公開解決ラベルから取らない。
候補ごとに、シャンテン最小、受け入れ枚数最大、種類数最大、牌種番号最小の順で後続打牌を選ぶ。
一つの後続打牌のシャンテンと受け入れを対にして使い、異なる打牌の最良値をつなぎ合わせない。
合法な後続打牌が空なら特徴エラーとし、教師候補を黙って削らない。
この集約は鳴き後の手牌効率を示す特徴であり、相手が実際にその打牌を必ず選ぶという方策ではない。

槓候補では未公開の嶺上牌と新ドラを入力に加えない。
加槓への応答中も、現在の実装と同じく公開解決前の新ドラを参照しない。
将来の嶺上自摸を積分したEVを、この受け入れに含めない。

例えば自家にある1枚を切ると、`h`が1減って`v_a`が1増えるため、その牌の残数は増えない。
チーの対象牌を河と面子の両方で数えることもない。
この二つを独立した期待値付きfixtureにする。

## 5. 計算APIと高速化

新規モジュールは`tools/ev_policy_features.py`の一つにまとめる。
相手モデル側は公開状態の更新とモデル計算を担当し、形の計算、候補の投影、特徴キャッシュ入出力をこのモジュールへ置く。
循環importを避け、新規モジュールから`ev_policy_opponent`をimportしない。
cache入出力は通常のレコードを返し、既存`EncodedCandidate`への変換は相手モデル側で行う。
共通の既存シャンテン関数やアプリ用計算は置換しない。

```text
exact_shape(counts34, fixed_melds) -> {shanten, improvingMask}
project_action(view, action) -> {shanten, ukeireCount, ukeireKinds, applicable}
```

`view`は対象家の手牌、固定面子、公開枚数、応答対象牌を明示した値とする。
四家の私有データ全体や未来イベント列を渡さない。
既存`RoundFeatureState`からこの値を作り、将来のD.3.3も同じ計算APIを呼ぶ。
D.3.3の実際の接続は本段階では行わない。

まず既存`shanten`を最大34回呼ぶ参照実装と、上限付きの形キャッシュを作る。
同じ窓内で同じ`(counts34, fixed_melds)`へ到達する候補は再計算しない。
全件特徴の永続化と合わせて予算を満たせば、その構成を採用する。
速度のための近似受け入れ、候補の間引き、未知牌のサンプリングは使わない。

cold計算が予算を超える場合の次の実装候補は、色別の部分形を再利用し、四群の直積を段階的な到達状態の結合へ変える方法とする。
各群の`(面子数, ターツ数, 対子数)`を逐次合算し、同じ合計状態を重複排除する。
固定面子を含め面子数が4を超える状態以外は、正しさを示す前に枝刈りしない。
終端で現行の標準シャンテン式を適用し、門前時だけ七対子と国士の値との最小を取る。
加牌した群以外の部分結果を再利用する。
この高速経路も全受け入れmaskを参照経路と照合してから使う。
この順序により、巨大な全牌姿表や新しいネイティブ依存を最初から必須にしない。

## 6. キャッシュと特徴schema

形キャッシュと学習用特徴キャッシュは、入力境界が異なる。

| 層 | キーまたは同一性 | 保存内容 |
|---|---|---|
| 形のLRU | 計算版、34種の枚数tuple、固定面子数 | シャンテン、残数を適用する前の34bit mask |
| 学習用特徴 | dataset hash、特徴schema、コード依存hash、split、windowId、actorSeat、公開prefix hash、対象家の私有prefix hash、合法候補集合hash | 順序付き候補と対応する特徴、構造的一択の印 |

`roundId`、牌姿、巡目だけを学習用特徴のキーにしない。
同じ手牌でも見え牌が異なれば受け入れ枚数が違い、同じ公開prefixでも自家手牌が異なれば特徴が違う。
係数、lambda、温度は特徴の入力ではないためキーへ含めない。
ラベル、learningMask、公開解決は元の教師窓から`windowId`で結合し、特徴計算の入力へ渡さない。
将来期間と未指定期間の拒否、入力ファイルhash照合は、キャッシュ利用時も省略しない。

特徴は`ev-policy-opponent-features/v2`とする。
既存`local_acceptance`と`best_local_acceptance`は補助特徴として保持する。
具体行動特徴に`ukeire_count / 136`、`ukeire_kinds / 34`、`ukeire_applicable`を追加する。
種別特徴には`best_ukeire_count / 136`、`best_ukeire_kinds / 34`、`best_ukeire_applicable`を追加する。
種別内の最良候補も第4節の順で決め、同率の最終比較は`canonical_action`の文字列順とする。
既存の`best_action_shanten`と`best_local_acceptance`はその同じ候補から取る。
適用しない終局行動の0と、実際に受け入れ0の手牌をフラグで区別する。

モデルschemaとmodelVersionはv2へ進め、v1の係数を継ぎ足して使わない。
v1ファイルは保存し、v2ローダーは特徴名、順序、特徴版、計算版の不一致を明示的に拒否する。
再学習は全係数0から始める。

永続特徴は`calibration/features-opponent-v2/`へ、元の教師順を保つsplit別の連番shardとして保存する。
初版は標準ライブラリのgzip JSONLを使い、数値はfloat64へ往復できる表現にする。
一つのshardは最大10,000窓とし、全行列をメモリへ載せない。
新しいDBやpickleは使わない。
manifestにはschema、計算版、入力hash、コード依存hash、特徴名と順序、正規化定数、shardごとのhashと窓数と候補数を残す。
`.jsonl.gz`と一時ファイルはGit管理外、manifestと検証集計は管理対象とする。

書込みは一時shardから完了shardへ切り替え、全件照合後だけmanifestを`complete`にする。
再開は同一manifestの完了shardだけを再利用し、重複または欠落windowIdを検出する。
最終shardに達していないキャッシュ、hash不一致、異なるコードでの再開はfitとevaluateが拒否する。
debug標本は別ディレクトリと`debug`状態にし、全件版として採用できない。
一択応答の特徴計算は省いてよいが、教師順、件数、評価分母、確率1と勾配0は保つ。

## 7. 性能測定と予算

性能標本はtrain期間の教師メタデータから、seed `20260909`でwindowIdのhash順に20,000窓を固定する。
phaseごとに最大256窓を先に確保し、残りを全体のhash順で埋める。
phaseが不足した場合は不足件数を残す。
実選択ラベル、局末結果、confirmation指標は標本選定へ使わない。
合法候補に含まれる各行動種別を最大64窓ずつ補う別のedge標本も固定し、速度標本の平均へ混ぜない。
標本ID、元の順序、入力hash、予算を測定前のmanifestへ保存する。

参照経路、新経路のcold、warm、永続キャッシュ読込を同じ標本で測る。
coldは新規プロセスで始め、既存シャンテンLRUの温まりも区別する。
両経路の形計算件数、hit/miss、phase別時間、公開状態再構成時間、入出力時間、処理窓数、候補数、peak working setを記録する。
Windowsの実プロセスメモリを測り、Pythonオブジェクトだけの測定を代用にしない。
CPU、Python、NumPy、コードhashも記録し、別環境の時間を同一条件の速度比にしない。

| 予算項目 | 初期値 |
|---|---:|
| 20,000窓とedge標本の測定全体 | 1時間 |
| 全件特徴生成と検証 | 8時間 |
| 全件fitと再読込evaluate | 合計8時間 |
| 単一実行のpeak working set | 4 GiB |
| 特徴cache総量（一時shardを含む） | 8 GiB |
| 新しい形LRUの最大エントリ数 | 100,000 |

これらは開発作業を完走できるかの基準であり、D.4の予測精度の採用閾値ではない。
全件時間は標本の平均だけで合格にせず、全件実測で判定する。
推論のcold時間は報告するが、D.3.3の粒子法に必要な速度をこの段階で保証しない。
予算超過は`feature_budget_exceeded`として停止し、完了shardと診断を残す。
自動的な予算引上げや近似計算への切替は行わず、次の設計判断へ戻す。

## 8. CLIと再学習

新CLIは既存`tools/calibrate_ev.py`へ追加する。
以下は実装予定の契約であり、現時点で実行できるコマンドではない。

```powershell
python tools/calibrate_ev.py probe-opponent-features --output-dir calibration/probes/opponent-features-v2
python tools/calibrate_ev.py build-opponent-features --output-dir calibration/features-opponent-v2
python tools/calibrate_ev.py verify-opponent-features --feature-dir calibration/features-opponent-v2
python tools/calibrate_ev.py fit-opponent --feature-dir calibration/features-opponent-v2 --output-dir calibration/model-opponent-v2
python tools/calibrate_ev.py evaluate-opponent --feature-dir calibration/features-opponent-v2 --model-dir calibration/model-opponent-v2
```

新規CLIにも`--dataset-dir`を持たせ、既定は`calibration/dataset-opponent`とする。
buildの`--resume`は第6節の同一性条件を満たす場合だけ許す。
fitとevaluateは検証済みcacheを要求し、未指定時に旧v1へ黙って戻さない。
現行`model-opponent/`を上書きしないよう、v2実装時の既定出力先も`model-opponent-v2/`へ変更する。

2018-19〜2022-23を学習、2023-24を正則化選択、2024-25をphase別温度較正、2025-26を開発確認に使う。
labelDefinitionは`joint-public-resolution-v1`を維持し、学習mask、重み1、共同応答尤度、教師順と構造的一択の扱いも維持する。
lambda候補`[0.01, 0.1, 1, 10, 100]`、温度候補`[0.5, 0.75, 1, 1.25, 1.5, 2]`、学習率0.03、batch 256、2 epoch、seed 20260909を再学習前のmanifestへ固定する。
特徴schema以外のoptimizer変更を同時に行わない。

v1の保存済み集計との比較では、全体NLLだけでなく、自己行動NLL、公開応答NLL、Brier、phase別指標、行動率、支持件数を示す。
同一窓集合と分母を照合できる場合だけ比較値を出す。
改善を見てからconfirmationを再調整へ使わず、2025-26は今回も独立テストと呼ばない。
v2のfit時と再読込evaluate時の指標、支持件数、hold集合は一致させる。

`exact_candidate_ukeire`のholdは、全件の特徴検証と性能ゲートを通った場合だけ解除できる。
未識別成分、応答率、複数リーチ危険度、役形特徴のholdはそれぞれ再判定または維持する。
現在fitとevaluateで異なる採用判定は、同じhold集合から導く関数へまとめる。
D.3.2a完了後もこれらのholdが残る場合は`eligibleForD33=false`とし、開発計画を自動的にD.3.3開始へ進めない。
本段階では未実装特徴の存在からholdが残るため、後続の設計対象をレポートで提示する。
