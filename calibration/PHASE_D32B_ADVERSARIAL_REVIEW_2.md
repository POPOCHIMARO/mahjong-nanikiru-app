## 2. 今回の指摘

### S1 [P1] 端点を含む等間隔格子では、Jeffreys事前分布と正の下側分位点が未定義

対象：7.3節の手順3〜4（218〜219行）、7.6節の265行、D32B-08。

Beta(0.5, 0.5)の密度は、定数倍を除いて次式である。

```text
prior(p) ∝ 1 / sqrt(p × (1-p))
```

設計が指定する2,001点の等間隔格子は0と1を含む。
両端で密度は発散するため、単に各点の「尤度×事前密度」を正規化すると、未定義、無限大、または0×無限大を扱うことになる。
連続分布で事後平均が内点にあることは、この離散計算の妥当性を保証しない。

端の区間の確率質量を格子点0へまとめる方法で回避しても、2.5%点が0になる場合がある。
ゼロ見送り／100機会という合法な小例では、連続事後分布はBeta(0.5, 100.5)となる。

| 量 | 数値確認 |
|---|---:|
| 事後平均 | 0.0049504950495 |
| 2.5%点 | 約0.000004897 |
| 97.5%点 | 約0.0247449 |
| 最初の半セル `[0, 0.00025]` の確率質量 | 約17.72% |

この端セルの質量を0に置けば、離散分位点の2.5%点は0になる。
したがって「D.3.3用の下側は正の2.5%点」という7.6節の前提を満たせない。
これは特に見送り件数の少ない層別推定で発生しうる。

**修正条件：**

- 格子点の密度を使うのか、区間の積分質量を使うのかを定義し、端点処理を確定する。
- 共役な場合はBeta事後分布を直接使う、あるいは`p = sin²(u)`などの変数変換による積分を使う方法が候補になる。
- 分位点と事後平均の数値誤差を、解析解のある例または独立した高精度計算と比較する。単に同じ格子計算を二度行う試験では足りない。
- D.3.3で使う全定数について`0 < p < 1`と有限性をAPIで検査する。正であっても1なら残余行動の支持を失う。
- ゼロ見送り、全見送り、合法機会0、少数機会をD32B-08へ追加する。

### S2 [P1] ツモ見送り率を推定する自己行動の尤度が定義されていない

対象：7.3節の手順2（217行）、D32B-08。

推定対象にはε_tsumoを含むが、手順2は既存の`joint_resolution_likelihood`と同じ列挙による公開結果の尤度だけを指定している。
既存実装のこの関数は、捨牌者、各応答者の候補、公開応答結果を受け取る関数であり、ツモ自己行動窓を処理しない。
[ev_policy_opponent.py](../tools/ev_policy_opponent.py)の`window_nll`も、自己行動と共同応答を別経路で処理している。

応答窓だけから尤度を作るとε_tsumoに依存する項がなく、連続Jeffreys事前分布のままなら事後平均は0.5になる。
自己行動窓も既存関数へそのまま渡す実装なら、必要な入力構造が一致しない。
「同じ形で扱う」という7.2節の合成規則だけでは、推定時の窓の振り分けを定義したことにならない。

**修正条件：**

```text
log L(constants | θ)
  = Σ[有効な自己行動窓] log P(constants, θ)(観測行動 | view)
    + Σ[有効な応答窓] log Σ[公開結果と両立する希望]
                                      Π[各家] P(constants, θ)(希望 | view)

ツモ合法時：
  観測がtsumoなら  P = 1 - ε_tsumo
  その他なら      P = ε_tsumo × 残余候補上の学習分布
```

- 上のようにphaseごとの尤度を明示し、和了判定holdや学習マスクで除外する窓の条件も固定する。
- 100回すべてツモを取った例でBeta(0.5, 100.5)になること、見送りを追加するとε_tsumoの推定値が上がることを検証する。
- 隠れた希望に関するD32B-08の例に加え、自己行動の解析解との一致を要求する。

なお、他の定数を点固定して2巡更新した分布は、一般には各定数の周辺事後分布とは異なる。
ただし、本モデルの尤度が定数ごとに因子化するなら、その問題は生じない。
今回の応答小例では実際に因子化を確認したため、「2巡だから必ず誤り」とは判定しない。
採用する合法集合と応答解決について因子化を証明するか、依存が残る場合は条件付きの近似であることと、同時積分との差の検証を明記する必要がある。

### S3 [P1] 同じ支持集合とESS半減検査だけでは、重み替え後の事後分布を検証できない

対象：7.6節の267行。
関連：[PHASE_D3_DESIGN.md](PHASE_D3_DESIGN.md)の6節、7.2節、D33-04。

全行動確率が正なら、同じルールと同じθの下で理論上の経路の支持集合を共有できる。
しかし、有限個のbase粒子に、別シナリオで重要になる経路が実際に含まれるとは限らない。
欠落した経路は重み替えでは生成できず、ESSはその欠落を検出できない。

次の2状態例では、現在の再実行条件を通過する。

```text
base:     P(A)=0.9999, P(B)=0.0001
scenario: P(A)=0.1,    P(B)=0.9
N=256

baseの独立標本256個にBが一つもない確率：0.9999^256 ≈ 97.47%
全部Aだった場合：
  全粒子の尤度比 = 0.1 / 0.9999
  再正規化後は一様重み
  ESS_before = ESS_after = 256
  推定P(B)=0、真のscenario P(B)=0.9
```

これは粒子法特有の複雑さを含まない反例であり、理想的な独立標本でも成立する。
再標本化で同じ祖先を複製している場合は、ESSだけではさらに判別しにくい。

**修正条件：**

- ESS半減を再実行の十分な検出条件として扱わない。各シナリオの独立SMCを基準とし、重み替えを使う範囲はその比較検証から限定する方法が明確である。
- 再利用時も、祖先と手牌の多様性、独立反復間差を既存のD.3設計どおり診断する。これらだけでも未観測の状態を完全には検出できないため、独立再実行との照合を省略しない。
- 重要状態がbase標本から欠落する上の小例を追加する。

重み替えの式と保存する履歴も固定する必要がある。
上位設計の対象は潜在応答を含む全履歴`z=(x_0:t,c_1:t)`なので、同じθで定数だけを変えるなら、保存済み経路の重み替えは次式になる。

```text
W_s(i) ∝ W_base(i) × γ_s(z_i) / γ_base(z_i)
```

比は対象となる相手の全過去行動にわたる比であり、最後の行動だけの比ではない。
潜在応答を経路として保持しているならその希望の確率を使い、周辺化しているなら対応する周辺密度の比を使う。
両方を重複して掛けない。
自家の既知操作に相手モデルの尤度を掛けないこと、log空間で計算することも上位設計から引き継ぐ。

### S4 [P1] `known`への変更だけでは、和了判定の修正を確認できない

対象：4.2節（79〜87行）、4.3節の条件2（95行）、D32B-01。

現行の[ev_policy_observation.py](../tools/ev_policy_observation.py)では、`IllegalAction`を受け取ると、ロン候補を追加しないまま`winActionStatus=known`を返す。
つまり`known`は、合法和了と、和了できないことが確定した状態の両方を含む。

実際に`_score_ron`が`IllegalAction`を返す小さいスタブを`semantic_response_actions`へ渡すと、次が返った。

```text
actions = [pass]
winActionStatus = known
```

したがって、実際にロンした510席を誤って「既知の不合法」へ変えても、4.3節の`known`という検査だけは通る。
「修正後にfixtureが通る」という条件も、fixtureの期待値が`known`だけなら防げない。

**修正条件：**

- 実際に和了した窓では、正しい家の`ron`または`tsumo`が合法候補に含まれることまで確認する。既知の不合法として正しく処理すべき窓とは期待値を分ける。
- 924件の分類時に、修正後の期待候補、期待エラー、隔離理由のいずれを確認するかを個別に保存する。
- 得点や形の独立した期待値が得られる分類は、その照合もfixtureへ含める。

4.2節の検出器については、現在の記述だけでは次の境界が確定しない。

- 「和了判定の直前」が候補生成の入口か、得点器呼出の直前か。現行`_score_ron`と`_score_tsumo`は、得点器を呼ぶ前に待ち判定で不合法を返す。検出対象がこの前段にも関係するなら、得点器直前のフックだけでは届かない。
- detectorが偽を返した後、得点器が未知のエラーを返した場合の処理。
- detectorの入力に使ってよい情報、分類ごとの検出対象、検出漏れを調べる派生例。

現行コードは`hand_not_winning`を`IllegalAction`へ変換せず、`HandScoringError`として伝播させる。既知の不合法へ変換するコード集合は`{no_yaku}`である。
**この既存の安全側の動作を維持する試験**を追加し、detectorが偽であることだけを「対応済み」の根拠にしないこと。
detectorが真、偽かつ正常、偽かつ未知エラーの3経路を区別する必要がある。

また、79行の「未対応の手もhand_not_winningになる」という説明は原因調査前の仮説である。
実際に残った分類の機構に基づいて検出条件を確定し、既知の924件だけに一致する検出器を一般的な検出器として採用しない。
型や牌種の対称変換、赤区分、暗槓と副露の違い、前段の待ち判定で止まる例を検査する。

### S5 [P2] シナリオ名から4定数の値が一意に決まらず、「17」の実行集合も固定されていない

対象：7.3節の224行、7.4節の236行、7.6節の表、14節R4。

baseではε_chankanをε_ronから流用するが、OATやcornerでε_ronを変えたとき、ε_chankanも追従させるかが未定義である。
「1つの定数だけを変え、他はbase」を文字通り守る場合と、`chankan_uses_discard_ron_constant`をシナリオ全体の関係として守る場合では、搶槓の粒子重みと将来方策が異なる。

`stratum_extremes`も、複数の層と複数の定数の上下端を、一つの定数ベクトルにはできない。
各端を別シナリオにするか、組み合わせるか、その値を全局面に適用するか該当層だけに適用するかが必要である。

層別から展開する具体的なシナリオ数をKとすると、表からは次の数になる。

```text
base + OAT 6 + corner 8 + chankan_assumption = 16
D.3.3：16 + K
D.3.4：17 + K  （上にzeroを追加）
```

仮に`stratum_extremes`を1シナリオと数えるなら、D.3.3は17、D.3.4は18である。
該当層がなければK=0となる。
固定の「17シナリオ」だけでは、全実行集合を指定できない。

**修正条件：**

- 各scenario IDに`(ε_ron, ε_tsumo, ρ, ε_chankan)`、適用する層、θの識別子、事後分布の識別子を持たせる。
- ε_chankanの追従規則を明記する。
- `stratum_extremes`を具体的なIDへ展開する規則、K=0の処理、重複値の扱いを定義し、展開後の一覧をmanifestで固定する。
- 7.4節の参照先「7.5節」は「7.6節」へ修正する。
- `zero`はbaseの事後分布を使う将来方策だけのストレス試験なので、履歴と将来の両方を変えたシナリオとは別の種別として出力する。現行の「baseを使うと記録する」方針自体は妥当である。

ε_chankan=0.5は一つのストレス点であり、見送り率の不確実性全体を表す分布や上下限ではない。
これを単独の仮定検査と呼ぶなら採用できるが、未知の搶槓見送り率を広く覆ったとは解釈しないこと。

### S6 [P2] 区間が重ならない層だけを感度分析に入れると、最も不確かな層が除外される

対象：7.4節の236〜237行、7.6節の`stratum_extremes`。

全体の区間と層の区間が重ならないことは、層の差を検出するための条件には使える。
しかし、感度分析で変動させる必要がある層を選ぶ条件としては弱い。
広い区間ほど全体と重なるため、支持が乏しい層の不確実性をシミュレーションへ反映しないことになる。

例えば次の組では、層の上側が全体より大幅に大きくてもシナリオが追加されない。

```text
全体区間：[0.001, 0.003]
層の区間：[0.00001, 0.8]
区間の重なり：あり
現行のstratum_extremes追加条件：偽
```

これは実データの推定値ではなく、選択規則の反例である。
合法機会がない層のJeffreys事前分布の区間も広く、同じ問題が起きる。
層の件数を報告するだけでは、その層に入る前向き試行のEV感度は調べられない。

**修正条件：**

- 差が検出された層と、支持不足で値を絞れない層を区別して保存する。
- 感度分析の対象は、区間非重複だけでなく、対象判断と前向き試行で到達する層の不確実性を含める。
- 少なくとも「全体区間を包含する広い層」をシナリオから黙って除外しない。未検査として残すか、端点のストレス試験へ展開する。
- 層別尤度で三家のどの家の層にどの定数を割り当てるかも定義する。混在する応答窓を一つの「自家の層」へ機械的に分類しない。

### S7 [P2] 混一色距離が、すでに固定された数牌の種類と矛盾する

対象：6.3節の`flush_path`と`flush_distance`（167〜168行）、D32B-04。

固定面子の数牌が萬子なら、混一色を目指す数牌種は萬子に固定される。
現行式は`flush_path=true`のときも「手中で最多の数牌種」を自由に選ぶため、別の色で距離0を返せる。

```text
固定面子：123m
手中：22334455p + 西西  （鳴き後の打牌済み、10枚）

flush_path = true
現行flush_distance = 0   （手中の最多種は筒子、残りは字牌）
固定面子に合わせた不要な他色牌 = 筒子8枚
対応する距離 = 8/14 ≈ 0.571429
```

この形では筒子の混一色には移れないため、距離0は役の手掛かりとして逆方向の値になる。

**修正条件：**

- 固定面子に数牌種がちょうど1つあれば、その種類を対象にして手中の他色牌を数える。
- 固定面子がない、または字牌だけの場合に限り、手中の最多種を選ぶ。
- 固定面子が複数色なら現行どおり経路なしとする。
- 「固定面子の色と手中の最多色が異なる」固定例をD32B-04へ追加する。

## 3. 重点箇所について、問題としなかった点

### 3.1 7.2節の逐次合成

通常の応答集合にはpassがあるため、ロンと大明槓を除いた残余集合が存在する。
この条件では、εとρが[0,1]にあるとき、逐次合成の各確率は非負で合計1になる。
ρをロンしなかった条件下の確率とする再定義も一貫している。

ただし「ルールの優先順位」がこの行動確率モデルを一意に導くわけではない。
ルールが決めるのは複数家の希望の解決順であり、同じ家が何を希望するかを定数で表す部分はモデル仮定である。

残余集合が空の一般化した入力では、`L={daiminkan}`へ「残りをロンへ戻す」と不合法な行動が生まれる。
現行の通常応答APIではこの集合は生成されないため、P1の指摘にはしていない。
APIを汎用化するなら、この集合を拒否するか、唯一の合法行動へ確率1を与える規則にする。
同様に自己行動の`L={tsumo}`では、戻す先はtsumoである。

### 3.2 7.3節の共同応答尤度

方針自体は前回R3への正しい対応である。
既存の`resolve_joint_response`を使い、席1でロンが合法、席2で大明槓が合法な小例を列挙した。

```text
席1：P(ron)=1-ε、P(pass)=ε
席2：P(daiminkan)=ρ、残余をponとpassへ配る
席3：passのみ

P(公開結果が席1のron) = 1-ε  （ρは積分で消える）
P(公開結果が席2のdaiminkan) = ερ
```

この小例では、ロン結果に隠れた大明槓希望を負例にしない。
εとρの9組で全列挙と上式の一致を確認した。
ただし、正しい応答尤度の採用と、S1の数値積分、S2の自己行動尤度の定義は別々に検証する必要がある。

### 3.3 7.6節のOATと全8角

3定数について6つのOATと8つの角を調べる構成は、前回の「同時に上下させると相殺する」という反例に対応している。
これを追加したこと自体に問題はない。
連続領域全体で符号が不変だとは保証しない点も269行に明記されている。
今回の問題は、この離散シナリオ集合の定義と、各シナリオの事後分布を数値的に正しく評価できるかである。
