## 3. 初回に採用する出題条件

### 字牌候補の除外

14枚の手牌について、1シャンテンを維持する打牌候補の中に**字牌切りが1種類でも含まれれば、問題全体を除外する**。
現在の `analyzeDiscards(...).keep` に対して判定する。正解が字牌の場合だけを除く条件にはしない。

字牌を持つ手を一律に除外するわけではない。字牌の対子や刻子が残り、そこを切るとシャンテンが悪化する手は対象に残せる。
これにより、字牌の存在そのものと、比較すべき打牌に字牌が入ることを区別する。

### 四枚使いの除外

手牌14枚に同種4枚があれば、牌種や正解打牌にかかわらず問題全体を除外する。
正解がその四枚のうちの1枚を切る場合だけには限定しない。
これは牌効率モードが暗槓を評価しないことへの保守的な出題制限であり、四枚使いの価値が低いという麻雀上の判断ではない。

### 維持する条件

- 実際のツモ前13枚が2シャンテンで、ツモ後の打牌により1シャンテンへ進む。
- 正解は受け入れ枚数最大。同数時だけ現在の変化枚数で比較し、最終正解は1種類。
- 2ツモ以内の進展率で別候補に逆転される問題は除外する。
- 同率の扱い、通常難度と高難度の受け入れ差、難度選択の既存比率を維持する。
- 生成できない場合も条件を緩めず、既存の失敗表示と再試行を使う。

孤立字牌を残す旧反例は引き続き出題しない。残り枚数計算、シャンテン計算、清一色用の暗槓計算は変更しない。

## 5. Q1：出題条件を実装する

### 実装前に固定するもの

1. `git status --short` と対象ファイルの差分を確認し、既存の変更を保護する。
2. [保存済み200問標本](calibration/ankan-opportunity-analysis/generated-sample.json)のエンジンhashと現ファイルを照合する。同じであれば内容の旧比較標本として再利用する。
3. 同じ端末、Node、乱数方式とseedで通常20問と高難度20問の生成時間を測れる小さな計測経路を用意し、編集前の基準値を保存する。旧200問標本の総時間だけからp95を推定しない。

### 変更の要点

- 四枚使いは、手牌の枚数が確定した直後に安く判定する。
- 字牌候補は、最小シャンテンと維持候補が分かった時点で判定する。
- いずれも高価な変化計算と2ツモ列挙より前に除外する。
- 生成器の通常のreturnだけでなく、探索上限時の有効候補へのフォールバックにも同じ条件を適用する。
- `efficiencyAnswerIsSound` などテストから使う出題適合性の判定と、実生成の判定を揃える。必要なら小さな共通判定へまとめ、別モジュールの追加は避ける。
- `analyzeDiscards` は一般的な計算結果を返す関数のままにし、字牌候補や四枚使いを計算結果から消さない。清一色と押し引きも参照するため。
- 孤立字牌の罠型を、牌効率の生成対象として扱わない。解説やテストの定義も矛盾なく整える。汎用の検出機能を残す場合は、検出可能であることと現在出題することを区別する。

### 固定ケース

| ケース | 期待する結果 |
|---|---|
| `12344m46788p567s4z` | 現在は北切りが正解として通るが、修正後は字牌候補があるため出題不可。打牌分析の数値自体は変えない |
| 数牌が正解だが、字牌も1シャンテン維持候補になる手 | 正解だけを見て通さず、問題全体を除外。保存標本から全14枚を固定する |
| 字牌の対子／刻子はあるが、字牌切りはシャンテンを悪化させる手 | 字牌があることだけで除外しない。四枚使いなしで既存の品質条件も通る対照例を固定する |
| `567m38p334444555s` と `678m38p334444555s` | 報告された13枚に5m／8mを加えた14枚。いずれも四枚使いとして出題不可 |
| 四枚使いはあるが、別の牌を切るのが正解の手 | 四枚から切る場合だけを弾く実装にしない。保存標本から固定する |
| 数牌だけで四枚使いのない有効手 | 通常と高難度、同数タイブレークを含む既存の有効手を残す |
| `24567m15667p123s4z` と `24567m15667p1239s` | 旧反例を再び出題しない。後者で字牌に依存しない2ツモ逆転排除を確認する |

固定ケースは14枚、各牌4枚以下を明示検査する。全牌姿が不明な記憶上の7889例を、再現済みのケースとして追加しない。
新条件を適用した後に旧「健全な北切りは通る」テストが落ちることは、意図した仕様変更である。一方、受け入れや枚数保存のテストが落ちた場合は計算の退行として調べる。

**Q1完了**：除外と許可の固定ケースが通り、実生成と適合性判定の条件が一致する。

## 7. Q3：出題内容と待ち時間を確認する

### 内容の確認

通常100問、高難度100問の計200問を固定seed 20260911で生成し、修正後の別ファイルへ保存する。
既存の `sample-generator.js` は出力先が修正前の `generated-sample.json` に固定されているため、そのまま実行して旧標本を上書きしない。出力先を引数化するか、新しい検証経路を使う。
標本には手牌14枚、ツモ前13枚、ツモ牌、正解、維持候補、難度、罠型、seed、エンジンhashを残す。

| 指標 | 合否／扱い |
|---|---|
| 字牌の維持候補を含む問題 | 0／200 |
| 四枚使いを含む問題 | 0／200 |
| 生成失敗、枚数異常、正解条件違反 | 各0／200 |
| 通常と高難度の問題数 | 各100 |
| 浮き牌、唯一の対子、二度受けなど | 件数を報告する。配分を同じ数へ強制しない |
| 重複した牌姿、受け入れ差の分布 | 件数と分布を保存し、極端な集中がないか確認する |

最終標本から通常10問と高難度10問を固定ルールで選び、採点理由が説明に反映されているかを見る。
同じ牌姿の繰り返しや、残った特定の罠型だけへの集中があれば、その例を記録して生成条件を限定調整する。
20問の確認を、すべての実戦判断や学習効果の保証とは呼ばない。

### 性能の確認

Q1で定めた同一条件の通常20問と高難度20問について、修正前後の中央値、p95、最大値、生成失敗件数を記録する。
測定中に他の重い集計を並走させない。乱数列が同じでも採用される問題は変わるため、1問ずつ同一牌姿の比較とは扱わない。

初回の受入目標は**生成失敗0件、p95が修正前以下**とする。これは実戦頻度から導いた値ではなく、機能修正で待ち時間を悪化させないための運用目標である。
ノイズが疑われる場合だけ同じ条件で1回再測定し、それでも悪化するなら完了扱いにせず原因を調べる。
相対的に改善しても操作中に画面が固まるほど遅ければ、その実測を未解決事項として残す。

### 供給不足や遅延が出た場合の順番

1. 高価な計算前の除外と重複計算の有無を確認する。
2. 出題不能な孤立字牌の罠を探して待っていないか確認する。
3. 罠型の探索比率や追加探索の長さを、計測結果を根拠に必要最小限調整する。最初から新しい均等配分を設けない。
4. それでも満たせない場合だけ、生成方法の変更を別工程として提案する。字牌／四枚使い／正解の健全性の条件を無断で緩めない。

必要な検証が通った後、別seedや大量標本を無条件に追加しない。新しい失敗、偏り、条件変更がある場合だけ追加する。

**Q3完了**：内容の必須条件と性能目標を満たし、修正前後の標本と計測条件、結果が別々に保存される。
